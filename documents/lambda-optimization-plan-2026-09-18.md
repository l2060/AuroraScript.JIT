**Lambda / callable 正向优化实施方案 · 2026-09-18**

依据：`lambda-change-review-2026-09-18.md` 的源码审查、HEAD 对照复现及 IL 规模测量。本方案规划实施，不代表下述源码修改已经完成。

**目标与取舍**

本轮目标是把现有 callable 优化收敛为“可证明安全的共享 native 调用 + 既有通用动态调用”，保留已经验证的 IL 缩减收益，消除回退语义分叉，减少编译器维护的协议和状态。

实施顺序：整理已有基线 → 完成全部正确性修复 → 完成调用路径收敛 → 完成重复契约发现合并 → 统一测试与测量验收。扩大一等函数值的类型传播属于后续独立工作。

**执行约束：不为每次变更、每个提交或每个优化阶段安排测试任务。P0～P3 只做实现、源码阅读、引用检查和差异审查；全部优化完成后，才在 P4 集中补齐回归测试、执行测试及性能对照。下文各处“验收”仅表示 P4 的检查标准，不表示阶段内启动测试。**

不将全局类型推断、闭包单态化、任意宿主 delegate 适配或 nullable 语法纳入本轮，也不为每个 arity 建立新的调用器。

**一、先确定一致的语义，避免边改边补规则**

| 场景 | 本轮采用的规则 |
| --- | --- |
| 弱 callable / 无完整返回契约 | 保留既有动态行为；已支持的参数预测仍只在带 guard 的地方使用 |
| 与 callable 不匹配的函数值 | 保留既有警告及允许动态执行的政策，不升级为一律编译失败 |
| native 探测未命中 | 动态目标收到原始脚本实参；不得提前窄化数值、改变 ValueKind 或丢失对象身份 |
| native 探测命中 | 遵循与该目标普通动态入口相同的参数约束及执行语义 |
| 非 void 返回契约 | 保持已有返回检查与转换，不新增隐式强制转换规则；native / fallback 一致 |
| void callable | 调用者丢弃目标实际返回值；值位置统一得到 null，语句位置不保留结果 |
| 默认参数、参数数目不符、spread、宽调用 | 保留通用调用的实参行为与既有诊断，不因不满足优化条件导致编译器崩溃 |
| 参数求值 | 目标和实参按语言规定顺序求值一次；调用者参数求值期间不能提前切到被调闭包上下文 |
| 异常 | 保持 frame 恢复、参数缓冲区释放、finally 和脚本栈信息，不因优化路径不同改变责任边界 |

void 规则是对既有不一致的明确修正，应更新文档及测试。它不同于“必须保持当前所有错误结果不变”。

**二、P0：整理已有基线与预期行为，不重新运行测试**

工作内容：

1. 保存开始实施时的相关源文件清单及内容哈希，涵盖未跟踪的两个 callable 文件；不依赖单个 Git 提交代表整个工作区。
2. 直接引用审查报告已经复现的 Number → int64 回退、1.5 → int32 回退、8 参数越界、void 分支差异和多 callable 加法表达式问题，记录修正后的预期行为。最小回归测试的整理及运行统一放到 P4。
3. 保存已有“同签名 1 / 10 / 100 个调用点”的体积数据及样例定义，作为 P4 的对照输入，本阶段不重新测量。
4. 登记唯一既有核心测试失败：CLR warning 的诊断集合正常但错误输出为空。源码归因可在实现期间进行，需要执行的基线对照统一放到 P4，不能混入 lambda 收益统计。

后续 P4 的测试落点为现有 `CallableFunctionTypeTests`、相关 context / module tests，以及现有 benchmark 基础设施。优先在现有文件中扩展，不搭建新的测试框架。

完成标准：已有证据与预期行为书面固定；工作区、HEAD、后续修正版本可明确区分。性能比较不得用执行错误的 HEAD 样例充当有效速度基线。

**三、P1：修复三个确定问题，采用最小安全边界**

**P1.1：共享 thunk 只接受能够保留原始脚本值的预转换。**

涉及 `TypedCilEmitter.Callable.cs`、`TypedCilEmitter.CallableThunk.cs`。

当前 `CanPassNativeArgument` 表示参数可以经过检查或转换进入 native ABI；它不表示转换在 native 探测之前执行是安全的。这两个条件必须分开。

在现有计划构造或 thunk 资格判断中，增加一个局部、明确的实参可往返检查；使用已经存在的表达式类型事实和 native object 事实。检查要同时考虑实参的实际表示及目标参数表示，而不是只检查目标类型。

- 第一版只放行已经证明不会改变脚本种类、值和对象身份，且不会提前新增类型检查异常的转换。
- `Number → int64/uint64`、可能失败的 `Number → int32/uint32` 等转换不进入此共享 native 路径。
- unknown / Dynamic 实参不以预测类型冒充确定事实；无法证明就走已有通用调用。
- NativeObject、String、Object 等引用表示需验证 null 和对象身份，不能仅凭都属于引用类型放行。
- packed array 的底层存储表示本轮不新建适配 thunk。

这些调用走通用动态入口后，如果目标本身具有声明参数约束，仍由目标现有入口完成其应有检查。这会缩小一部分优化覆盖，但不削弱脚本功能。

不在本轮把所有 thunk 改成“每个实参同时传原始 Datum 和 native 值”：它会增加签名、转换和状态维护，且会削弱已有精简效果。也不引入另一套允许窄化的 thunk 家族。

验收：审查中的两项数值回归恢复既定语义；native 命中与同一目标的普通动态入口等价；fallback 与同一动态目标的直接调用等价；副作用实参只执行一次。

**P1.2：把返回契约解析与 native 优化资格分开。**

当前计划同时承担返回契约、delegate 签名与 native 资格，导致“不能 native 优化”时容易连返回语义也一起丢掉。

本轮只在已有方法或 `CallablePlan` 上做小幅拆分：先识别调用目标的 callable 契约及返回处理，再尝试构造 native 参数 / delegate 信息。未获得 native 计划，也能执行既定 void / 返回处理。不增加新的分析 pass 或通用计划继承体系。

native thunk 第一阶段限定在已有固定 arity 支持范围 0～7，且参数个数匹配、没有 spread。超过范围直接使用现有 `EmitCall` 的 `InvokeMany` / 参数缓冲区实现。

对 callable 动态 fallback 复用该通用调用实现，随后执行统一的返回处理。避免再手写一次参数循环和 `Invoke[count]` 索引。调用关系必须单向，不能让动态 fallback 重新进入 callable 分派形成发射递归。

`TryResolveCallableSlot` 的“能否找到契约”和“能否优化 spread”也应拆开；spread 仅阻止 native 资格，不应自动抹掉已知 void 返回契约。

验收：0 / 1 / 7 / 8 / 16 参数均无编译器越界；默认参数、参数数目不匹配和 spread 保留已有动态行为；宽调用的 void 值位置也返回 null；异常时缓冲区能够释放。

**P1.3：统一 void 结果。**

动态调用完成后，void 契约必须 Pop 实际结果；若处于值位置，再生成 null。共享 thunk 保持相同语义。

不应为修复 void 差异新添一条独立快路径。优先把已有返回转换逻辑收敛为小型 helper，或让所有动态 callable 调用都经过同一个返回处理出口。

验收：native 命中、缺少 native 入口、参数不适合 native、宽调用与 spread 的 void 行为一致。非 void 返回检查保持原有约束。

P1 完成条件：三个确定问题的修改完成并经过静态审查，随后直接继续 P2。可以保存此时的源码检查点 B1，但不运行测试，也不宣称该检查点已经通过正确性验证。到 P4 时，先验证 B1 对照工作负载的正确性，再将其用于性能比较。

**四、P2：删除重复调用协议和无效状态**

依赖 P1 的统一返回处理完成后实施。

调用发射目标结构：

```text
解析已有 callable 契约
  ├─ 能证明共享 native 调用安全
  │    └─ 共享 thunk
  │         ├─ 兼容 native target → 调用并恢复 frame
  │         └─ 未命中 → 使用保留原语义的参数执行动态调用
  └─ 其他情况
       └─ 既有通用动态调用 → 统一契约返回处理
```

移除主 `TypedCilEmitter.cs` 中剩余的 callable 内联 guard / try-finally / fallback 实现。不能进入共享 thunk 的 packed array 等场景先走通用路径。不要通过在 helper 中保留原内联协议，制造“删了主文件、复杂度仍在”的假简化。

这一取舍在 P4 统一通过 packed array / native object 热路径对照测试与测量检查：若出现重要场景可重复的性能退化，先检查已有通用入口能否改善；确需额外优化时另列有证据的小任务，不在本轮悄悄恢复第三条协议。

清理确认无消费者的状态：

- `PreparedDirectMethod.NativeParameters`、`NativeReturnType`。
- `CallablePlan.Slot` 及无必要的传递参数。
- 失去调用者的 `RecordContextualNativeParameter`。

清理前仍需执行全仓库引用检查，防止实施期间其他变更已经新增消费者。`NativeEntryTakesContext` 暂不机械删除，先核对 loaded imports、runtime closure 和持久化兼容；没有收益时保持现状。

验收：源码层面仅剩共享 thunk 与通用调用两种主要 callable 执行路径；所有边界测试通过；同签名 thunk 数不随调用点增加；本阶段编译器源码净减少。

**五、P3：只合并重复的契约发现，不重写类型系统**

涉及 `CallableContractAnalyzer`、`TypedFunctionBuilder`、`TypedFunctionCode` 和 `ModulePlan`。

必须保留两种事实之间的区别：确定的声明 / 上下文约束可以决定 ABI；预测信息只能支持带 runtime guard 的优化。合并发现过程不等于把所有预测都提升为强类型，也不等于删掉部分契约的预测能力。

建议的最小迁移：

1. 在既有契约分析阶段统一定位直接调用的 callee、lambda / 函数值及参数对应关系，复用已有 declaration 和 function ID 索引。
2. 复用 `ModulePlan` 现有 contextual parameter 记录机制，完整契约和部分契约都在这里发现；仍按原有条件决定是否应用声明或提供预测。
3. 让现有 TypedFunctionBuilder 消费同一记录，静态核对完整契约、部分契约与冲突处理的条件，再删除重复发现逻辑。native 方法签名、诊断和运行结果的对照统一放到 P4。
4. 保留 `ApplyContextualParameterPredictions` 的守卫语义；只有证明冗余的数据复制才删除。
5. 保留当前显式处理冲突的机制。不能因首次遇到一个契约，就覆盖更强的已有声明或让后续矛盾信息失效。

不要求本轮把所有推断类型从 AST 迁出。AST 不可变、完整 BoundCallable IR 或全局固定点求解会显著扩大修改范围，应等实际增量编译问题或更多类型流需求出现后单独讨论。

验收：直接 lambda、具名函数、部分契约、跨模块导入和宿主 HTTP 的既有结果、警告与 native 资格保持正确；每模块只建立一次必要索引；类型分析不再反复扫描整个函数集合来寻找同一个 lambda。

如果移除某段重复发现需要重排多个既有分析阶段，则本轮止于共享查询 / 索引，记录剩余工作，不为了形式上的“单一入口”重构整个编译流水线。

**六、宿主回调与模块状态：维持边界，避免扩散**

HTTP 的 `CallableType`、nullable response 和 detached 调用保留。将成功、超时 / 失败、null response、捕获 lambda、被嵌套 lambda 捕获的参数、显式参数类型和异常上下文纳入 P4 的统一验证。

暂不扩展 `TryInvokeNativeDetached<T1,T2>` 为全 arity 家族，不新增按返回类型或宿主包分别实现的调用桥。逐参数 nullable 与多 callback 元数据也不在本轮补齐。

跨模块 native 状态判断保持保守：只有已证明不依赖被调模块状态的入口才允许相应直调；不确定时回退。保留读、写、间接调用的跨模块测试，在 P4 一并运行。

新增模块状态不动点算法本轮先保持现状，在 P4 做逆序调用链与递归环的规模测量；仅在出现可重复瓶颈时另行提出反向依赖工作队列改进。不为了理论复杂度把它提前改造成另一套通用分析框架。

**七、P4：优化全部完成后，统一测试与性能验收**

P4 只有在 P1～P3 的实现和静态审查全部完成后启动。统一执行顺序：集中整理最小回归测试 → 构建最终候选及所需对照版本 → 执行语义、边界与相关完整回归 → 执行 IL / 编译成本 / 运行性能对照 → 出具一份汇总结果。

不在每项优化完成时提前运行对应测试，也不按修改文件逐一触发测试。如果最终统一测试发现问题，先集中归因并修复同类失败，再复验受影响项；需要时做最终整体回归。复验由真实失败或实质修改触发，不恢复成“每改一处就跑一轮”。性能测量在语义正确后开展。

| 维度 | 最低覆盖 |
| --- | --- |
| 执行模式 | Dynamic、OnlyRun、Persistence（按目标框架能力运行） |
| 入口 | native 命中、动态回退、混合目标、捕获闭包 |
| 参数 | 0 / 1 / 7 / 8 / 16，缺少 / 额外参数、默认值、spread |
| 值 | Number、int32、int64、String、Object、NativeObject、null、packed array |
| 返回 | 普通值、void 值位置、void 语句位置、错误返回类型 |
| 控制流 | 带副作用实参、目标变化、try/finally、异常后继续执行 |
| 模块 | 本模块、跨模块、导入已加载模块、现有热更新路径 |

采用有代表性的组合与边界覆盖，不建立上述维度的笛卡尔积测试库。优先断言脚本行为；结构测试只约束共享数、实现体数和体积，避免大量断言具体 opcode 排列。

性能样例：

- 同一签名的 1 / 10 / 100 / 1,000 个调用点，确认 thunk 固定、IL 随调用点近似线性增长。
- 小型高频函数值调用，分别测 native 命中、动态未命中和混合目标。
- packed array、native object 和捕获 callback 各一个代表性热点，检查保守回退的实际成本。
- 无 lambda 的普通模块，检查新增分析开销；100 / 1,000 函数模块检查重复查找成本。
- HTTP 使用本地可控服务验证行为；dispatch 微基准单独测量，避免网络波动掩盖结果。

记录编译耗时、编译分配、首次执行、预热后吞吐及分配、生成方法数、方法体 IL。复用已有 benchmark 项目，每个关键对照使用至少三个独立进程并报告波动，避免只取最快一次。

建议以“关键工作负载出现可重复且超过噪声的 5% 退化”为调查触发条件，而不是机械通过 / 失败标准；重复确认并定位后再决定保留与否。不能以修复错误后的运行结果去和执行无效 IL 的旧版本比较吞吐。

本轮收益预期是：正确性恢复、重复 IL 保持显著减少、编译器源码及重复分析减少。吞吐提升属于测量结果，不预先承诺百分比。

**八、防止代码膨胀的具体约束**

硬约束：

- 每个函数至多一份额外 native 实现体；不按调用点、参数值组合或捕获环境组合克隆函数体。
- 同一模块的相同签名及相同转换语义共享 thunk；缓存键不包含无关的调用点位置。
- 主调用协议最终收敛为共享 thunk 与既有通用动态入口；不保留第三套平行 fast/fallback 实现。
- 不新增逐 arity runtime 调用器，不按 HTTP / Timer 等宿主分别实现参数类型推断。
- 无消费者的计划状态不长期保留；新增计划字段必须有明确生产者和消费者。

规模目标：P1～P3 完成后，相对实施起点的 `src/Compiler` 源码争取净减少。分别报告新增、删除、净变化，包含未跟踪源码；拆文件、移动代码、压缩格式不计作复杂度收益。正确性所需的小量净增长可以说明，但不能用它为继续增加特化框架背书。

| P1 | 数值回退安全、宽调用、void 统一 | 中 | 修复实现及静态审查记录；可保存 B1 源码检查点 |
| P2 | 统一动态入口、移除内联协议和死状态 | 中 | 调用协议收敛、死状态清理及源码变化统计 |

实现可以按职责整理成可审查的提交或补丁，但提交边界不触发测试。全部实现完成后统一验收；若最终测试或基准暴露问题，只调整相应优化，保留仍然成立的正确性修复。当前工作区已混有多类变更，实际整理提交时只纳入本方案负责的修改，保留原有用户改动。

本轮完成的定义：三个确定问题解决，核心新增测试通过，已有失败完成归因 / 处置，调用协议收敛，IL 不再重复膨胀，关键场景无未经解释的可重复性能退化。目标框架或执行模式未验证的部分明确记录，不能以 net10.0 通过替代其他受支持目标的结论。

如果达到这些标准，就结束本轮，不以“lambda 还可以更强”为理由继续扩大范围。

**后续可选工作：仅当真实热点需要时推进**
